# Project charter

A charter is the "why and what" on one page. A spec is the "how". Write the charter first when the goal is fuzzy or involves more than one project or agent.

## Shape (one page)

```markdown
# Charter: <name>

## Mission
What changes for Dan when this works. Two to four sentences, with the number that proves it.

## Who it's for
Each person or role and what they get.

## Principles
Three to six rules that settle future arguments (e.g. "read the source, never a copy", "nothing goes to the team without a yes").

## Scope
| Does | Does not |

## How it's measured
| Area | What it does | How Dan uses it | Measure |

## Milestones
1. <name>: what's true when it's done. (No dates.)

## Out of scope
## Open questions
```

## Rules

- Measures must be things Dan can see: a message arrives, a number matches, a task disappears.
- Milestones are outcomes, never dates or durations.
- Name what Dan decides and what agents may do alone.
- If the charter implies a build, end with: "Next: spec <project> (say 'spec this out')."
